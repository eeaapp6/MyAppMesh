# APPMesh 软件需求规格说明书

**文档版本：** V1.0  
**文档性质：** 面向重新开发的软件需求规格说明书  
**适用对象：** 产品负责人、系统架构师、开发人员、测试人员和部署人员

> 本文档描述 APPMesh 应达到的产品能力、外部行为和验收标准。开发团队可自行确定内部技术方案，但必须满足本文档规定的需求。

## 1. 引言

### 1.1 编写目的

本文档用于指导在 FastCAE/FITK 框架基础上重新开发一个功能等价的 APPMesh 软件，并为设计、编码、测试、部署和验收提供统一依据。

### 1.2 项目背景

APPMesh 是面向几何模型和网格数据处理的桌面 CAE 应用。系统需要完成几何导入、网格生成、网格显示、网格文件交换和工程文件管理，并支持通过插件接入不同的几何内核、网格生成器和外部程序。

### 1.3 产品目标

1. 为用户提供统一的几何与网格处理工作环境。
2. 支持多种几何文件、网格文件和工程文件。
3. 支持 Gmsh、TetGen、FastCAE Grid 等网格能力扩展。
4. 对耗时操作提供后台执行，保持界面可响应。
5. 通过 FastCAE 的基座和组件降低基础设施开发成本，提高系统可维护性和扩展性。

### 1.4 术语

| 术语 | 说明 |
| --- | --- |
| FastCAE/FITK | APPMesh 所依赖的 CAE 应用开发框架、接口和组件体系 |
| 几何对象 | 由 BREP、STEP、STP、IGES 等文件导入的 CAD 模型对象 |
| 网格数据 | 节点、单元、边界集合及其附加信息的集合 |
| 网格生成器 | 负责根据几何和参数生成网格的引擎或外部程序 |
| 工程文件 | 保存几何、网格、插件数据和运行信息的 HDF5 文件 |
| 插件 | 在不修改主程序核心代码的前提下增加功能的动态模块 |

## 2. 产品范围与边界

### 2.1 产品范围

本版本覆盖：

- 桌面图形界面和三维模型查看；
- 几何文件导入；
- 网格数据管理和网格生成；
- 网格显示、点选、框选和预选；
- FITKMesh、CGNS、Gmsh、Abaqus 等文件操作；
- HDF5 工程保存和打开；
- 插件加载和管理；
- Python、HTTP 和 AI 扩展入口。

### 2.2 不在当前范围内或尚未确认的内容

- 物理场建模和求解器管理；
- 完整的结构后处理流程；
- 复杂 CAD 建模编辑；
- 分布式/集群网格计算；
- 所有插件的具体参数界面和算法能力。

## 3. 用户角色与使用场景

### 3.1 用户角色

| 角色 | 主要目标 |
| --- | --- |
| 普通网格用户 | 导入几何、生成网格、检查网格并导出文件 |
| 高级用户 | 管理多个网格引擎、插件和工程数据 |
| 自动化用户 | 通过 Python 或 HTTP 批量执行文件和网格操作 |
| 开发/部署人员 | 安装插件、配置运行环境并维护第三方依赖 |

### 3.2 主要使用场景

#### UC-001 几何到网格

用户启动软件，选择工作目录，导入 STEP 几何文件，检查三维模型，选择网格生成器并设置参数，执行网格生成，查看结果，最后导出网格文件并保存工程。

#### UC-002 打开已有工程

用户打开 HDF5 工程文件，系统在项目类型、文件版本和插件可用时尽力恢复几何、网格及插件数据；无法恢复的插件数据应给出诊断。

#### UC-003 自动化处理

用户通过 Python 或 HTTP 接口提交文件和网格任务，系统执行操作并返回结果或错误信息。

#### UC-004 插件扩展

开发人员部署新的网格插件。系统启动时发现并加载插件，插件向界面注册操作入口、向网格管理器注册网格类型，并参与工程读写。

## 4. 总体架构与复用要求

### 4.1 分层架构

```text
FastCAE 基座
    ↓
FastCAE 可复用组件
    ↓
APPMesh 框架扩展
    ↓
APPMesh 业务界面与业务流程
```

### 4.2 FastCAE 复用要求

系统应复用 FastCAE/FITK 提供的以下能力：

1. 应用生命周期、全局数据、组件和插件管理；
2. 数据对象、数据管理器、操作器仓库和线程池；
3. 几何、网格、IO 和 VTK 算法抽象接口；
4. VTK 三维窗口、通用 Widget、消息窗口和文件 IO 组件；
5. Python 桥接和视图适配器机制。

APPMesh 应通过应用工厂、组件工厂、操作器、插件和数据对象扩展这些能力，不应重复实现同等的通用基础设施。

## 5. 功能需求

### 5.1 应用启动与退出（FR-APP）

#### FR-APP-001 应用启动

系统应提供桌面应用启动入口，完成环境检查、配置读取、全局数据创建、组件创建、插件加载、主窗口创建和初始化，并在初始化成功后进入事件循环。

**验收标准：**

1. 正常环境下能够启动主窗口；
2. 初始化失败时给出错误信息并返回失败状态；
3. 支持无图形或 HTTP 服务启动模式（如果部署版本启用该功能）。

#### FR-APP-002 环境检查

系统应检查线程数、内存、磁盘空间和 VTK 运行环境；检查失败时应提示用户。

#### FR-APP-003 配置管理

系统应读取和保存应用配置、工作目录、插件配置和最近文件信息。配置文件格式和存储位置由设计阶段确定，但必须支持版本演进和异常恢复。

#### FR-APP-004 安全退出

系统退出时应等待后台任务结束，停止自动保存，写出配置和历史文件，并释放主窗口、组件、插件和全局数据。

### 5.2 工作目录和命令行（FR-WB）

#### FR-WB-001 工作目录

用户应能够查看和修改工作目录；文件对话框默认使用当前工作目录。

#### FR-WB-002 命令行输入

系统应支持通过命令行传入几何文件和工程文件。BREP、STEP、STP 文件应进入几何导入流程；HDF5 文件应在工程模式下进入工程打开流程。

#### FR-WB-003 工作流输出

在 WorkBench 模式下，系统应能够在任务结束时保存工程输出文件，并等待相关后台任务完成。

### 5.3 几何模型管理（FR-GEO）

#### FR-GEO-001 几何文件导入

系统应支持导入 BREP、STEP、STP、IGES 等几何文件。

**处理要求：**

1. 用户通过文件对话框选择文件；
2. 系统在后台任务中执行读取；
3. 导入成功后创建几何对象并加入全局几何数据；
4. 系统刷新三维显示和模型树；
5. 导入失败时不得留下不完整的几何对象。

#### FR-GEO-002 几何对象管理

系统应支持几何对象命名、树形展示、选择、显示/隐藏和删除。对象名称冲突时应自动生成合法的唯一名称。

#### FR-GEO-003 几何分组

系统应支持对几何对象或几何特征进行分组，并在模型树中反映分组关系。

#### FR-GEO-004 几何与网格关联

系统应保存网格与来源几何之间的关联信息，以便显示、工程保存和后续网格操作使用。

### 5.4 网格数据管理（FR-MESH）

#### FR-MESH-001 网格对象创建

系统应支持创建和管理多个网格数据对象。网格对象至少应包含节点、单元、网格维度、边界集合和关联几何信息。

#### FR-MESH-002 网格类型扩展

系统应允许网格插件按名称注册网格数据创建器。新增网格类型不应修改主程序核心管理流程。

#### FR-MESH-003 网格命名和生命周期

系统应支持网格对象命名、查询、删除和清理；删除插件或网格对象时不得遗留无效引用。

#### FR-MESH-004 网格组件和集合

系统应支持管理网格相关的模型组件、边界集合和附加数据，并允许显示和 IO 模块读取这些信息。

### 5.5 网格生成（FR-GEN）

#### FR-GEN-001 网格生成器接入

系统应支持通过插件接入 Gmsh、TetGen、FastCAE Grid 等网格生成能力。具体生成器是否可用取决于插件和外部程序部署状态；首版能力以实际加载的插件为准。

#### FR-GEN-002 生成参数

用户应能够选择网格生成器并设置其参数。参数由生成器插件定义，公共任务参数和生成器专属参数应分开管理；已实现的参数必须在界面中提供校验失败提示。首版不要求所有生成器具有统一的参数 Schema。

#### FR-GEN-003 后台生成

网格生成不得阻塞主界面。系统应显示任务执行状态，并支持成功和失败结果。首版不承诺统一的任务取消接口或 `Cancelled` 状态。

#### FR-GEN-004 生成结果

生成成功后，系统应创建对应类型的网格数据对象，写入节点、单元、边界集合和关联几何信息，并刷新模型树和三维显示。

#### FR-GEN-005 外部程序错误

外部网格程序不存在、启动失败、返回错误或输出文件格式错误时，系统应记录错误并向用户提示，不得破坏当前工程数据。

### 5.6 三维显示与交互（FR-VIS）

#### FR-VIS-001 三维窗口

系统应提供几何和网格三维显示窗口，支持旋转、缩放、平移和视角重置。

#### FR-VIS-002 显示控制

用户应能够控制几何和网格对象的显示/隐藏，并能够区分不同对象或集合的显示状态。

#### FR-VIS-003 点选和框选

系统应支持点选和框选几何面、网格单元或其他可拾取对象，并将选择结果传递给当前业务操作。

#### FR-VIS-004 预选高亮

鼠标移动到可拾取对象上时，系统应支持预选高亮；鼠标离开或选择状态变化后应正确清除临时高亮。

#### FR-VIS-005 图形同步

几何或网格数据发生新增、删除、修改和可见性变化时，三维窗口应能够刷新到最新状态。

### 5.7 文件导入导出（FR-IO）

#### FR-IO-001 网格文件导入

系统应支持导入 `FITKMesh` 网格文件，并将其转换为统一的网格数据对象。其他格式由已加载的 IO 组件或插件决定，不属于首版固定承诺。

#### FR-IO-002 网格文件导出

系统应支持导出 `FITKMesh`、`CGNS` 和 `Abaqus INP` 文件。其他格式由已加载的 IO 组件或插件决定。

#### FR-IO-003 文件格式错误

文件不存在、无法读取、格式不匹配或写出失败时，系统应提示错误，并保持当前内存数据不被破坏。

#### FR-IO-004 后台 IO

大型文件的读取和写出应使用后台任务，界面应保持响应，并在任务结束后通知业务层刷新状态。

### 5.8 工程管理（FR-PRJ）

#### FR-PRJ-001 新建工程

系统应支持创建空工程，并初始化几何、网格、插件和运行时数据。

#### FR-PRJ-002 打开工程

系统应支持打开 HDF5 工程文件，并按文件版本、项目类型和当前已加载插件尽力恢复几何、网格及插件数据。

#### FR-PRJ-003 保存工程

系统应支持保存和另存为工程文件。保存过程应收集当前插件数据并通过统一 HDF5 IO 机制写出。

#### FR-PRJ-004 工程状态

保存成功后，系统应更新当前工程路径和最近文件列表；保存失败时应保留当前工程状态并提示用户。

#### FR-PRJ-005 工程兼容性

工程文件应包含必要的版本和项目类型信息。无法识别或未加载的插件数据不保证恢复；系统应记录兼容性诊断，且不得因单个插件数据不可用而破坏当前内存工程。

### 5.9 插件管理（FR-PLG）

#### FR-PLG-001 插件发现和加载

系统应从配置或指定插件目录发现动态插件，并在启动时加载可用插件。

#### FR-PLG-002 插件安装

插件应能够注册 Ribbon 页面、操作器、组件和网格数据类型。插件安装失败时应记录原因。

#### FR-PLG-003 插件卸载

系统应支持安全卸载插件，清理其注册的网格创建器、组件和界面资源，不影响其他插件和当前核心数据。

#### FR-PLG-004 插件隔离

单个插件加载或执行失败时，系统应尽量保持主程序运行，并向用户提供错误信息。

### 5.10 Python、HTTP 和 AI（FR-EXT）

#### FR-EXT-001 Python 接口

系统应提供 Python 注册和调用机制，并暴露 APPMesh 文件操作和网格操作对象。当前已注册的业务包装包括 `Files` 和 `MeshGmsh`。

#### FR-EXT-002 HTTP 服务模式

在启用 HTTP 服务参数时，系统应加载 HTTP/Python 驱动组件，提供自动化调用入口。

#### FR-EXT-003 AI 助手

在非 HTTP 服务模式下，系统应支持加载 AI 助手组件和右侧 AI Dock。AI 资源初始化失败时应提示用户，但不应阻止核心网格功能启动。

## 6. 数据需求

### 6.1 几何数据

几何数据至少应包含对象 ID、名称、几何类型、拓扑/几何实体和显示状态。

### 6.2 网格数据

网格数据至少应包含：

- 节点坐标和节点 ID；
- 单元类型、单元连接关系和单元 ID；
- 二维、三维或混合维度信息；
- 边界集合和模型组件；
- 来源几何 ID；
- 网格生成器类型和生成参数；
- 显示状态和选择状态。

### 6.3 工程数据

工程文件应能够组织几何数据、网格数据、插件数据、生成参数、运行设置和必要的版本信息。

## 7. 接口需求

### 7.1 用户界面接口

- 文件菜单：新建、打开、保存、导入和工作目录；
- Ribbon 主页：导入、导出和插件入口；
- 模型树：几何、网格和对象状态；
- 三维窗口：显示和交互；
- 控制台：消息、日志和外部程序输出；
- 插件页面：由插件动态增加操作入口。

### 7.2 外部程序接口

网格生成器插件应能够配置外部程序路径、工作目录、命令行参数、输入文件、输出文件和返回状态。

### 7.3 模块接口约束

模块之间应优先通过 FastCAE 的抽象数据、组件、操作器和插件接口通信，避免业务模块直接依赖具体外部程序实现。

## 8. 非功能需求

### 8.1 性能

1. 几何导入、大型网格 IO 和网格生成不得长时间阻塞主界面；
2. 大型数据加载过程中应提供可观察的运行状态；
3. 图形刷新应避免重复创建不必要的显示对象。

### 8.2 可扩展性

1. 新增网格生成器应通过插件接入；
2. 新增文件格式应通过 IO 组件或适配器接入；
3. 主程序不应依赖某一个具体网格引擎。

### 8.3 稳定性

1. 文件读取失败不得导致程序崩溃；
2. 外部程序失败不得破坏当前工程；
3. 插件失败不得影响核心界面和其他插件；
4. 退出前应等待后台任务完成。

### 8.4 可维护性

系统应保持“基座、组件、扩展、业务”分层，界面、数据、操作器、图形和 IO 不应相互承担不属于自身的职责。

### 8.5 运行环境和部署

系统至少需要 Qt5、VTK、SARibbon、FastCAE/FITK 运行库和对应插件 DLL。Debug 和 Release 应分别部署到约定的运行目录，并确保 Qt 平台插件、外部网格程序和资源文件可被发现。

## 9. 异常处理要求

系统应覆盖以下异常：

- 配置文件不存在或无法写入；
- FastCAE 组件缺失；
- 插件不存在、版本不兼容或加载失败；
- 几何/网格文件不存在、格式错误或读取失败；
- 外部网格程序启动失败或异常退出；
- HDF5 工程损坏或包含未知插件数据；
- 后台线程创建失败或任务执行失败；
- 内存、磁盘空间或 VTK 环境不满足要求。

每种异常至少应提供用户可理解的提示，并在控制台或日志中保留诊断信息。

## 11. FastCAE 复用分析过程与选型依据

本节说明为什么选择 FastCAE，以及重新开发时如何从产品需求推导复用范围。FastCAE 是技术基础平台，不改变 APPMesh 的产品目标。

### 11.1 第一步：识别业务目标

APPMesh 的核心任务是几何导入、网格生成、网格显示、文件交换和工程管理。这些是产品业务目标；应用启动、线程池、插件加载、数据仓库和 VTK 窗口管理则是支撑业务的通用能力。

### 11.2 第二步：区分通用能力和领域能力

判断标准是：如果一项能力不依赖 APPMesh 的具体网格业务，并且可被多个 CAE 应用复用，就优先归入 FastCAE；如果一项能力体现 APPMesh 的网格业务规则、用户流程或产品界面，就由 APPMesh 自研。

| 能力 | 分类 | 选择依据 |
| --- | --- | --- |
| 应用生命周期、全局数据和插件管理 | FastCAE 基座 | 所有 CAE 应用都需要，且与网格业务无关 |
| 操作器仓库、线程池、消息和配置 | FastCAE 基座 | 通用基础设施，重复实现成本高 |
| 几何、网格、IO 和 VTK 抽象接口 | FastCAE 接口 | 便于替换几何内核、网格引擎和文件格式 |
| VTK 窗口、通用 Widget、控制台 | FastCAE 组件 | 技术复杂且可在多个应用复用 |
| CGNS、Gmsh、Abaqus 等文件读写 | FastCAE 组件 | 格式复杂，应复用成熟实现 |
| Gmsh、TetGen 等外部程序驱动 | FastCAE 组件 | 负责通用程序调用，业务流程由 APPMesh 决定 |
| APPMesh Ribbon、模型树和业务对话框 | APPMesh 自研 | 体现产品界面和用户流程 |
| 网格管理、插件参数和工程组织 | APPMesh 扩展/自研 | 体现 APPMesh 的领域规则 |

### 11.3 第三步：确定复用级别

FastCAE 能力按三种级别使用：

1. **必须复用**：应用生命周期、全局数据、组件管理、插件管理和基础接口；这些能力构成产品运行基础。
2. **优先复用**：VTK、几何内核、网格驱动和文件 IO 组件；除非有明确替代方案，否则不应重复开发。
3. **参考复用**：FastCAE 的界面控件或辅助组件可以替换，但替换后必须保持本报告定义的外部行为和验收结果。

### 11.4 第四步：把复用决策转成架构约束

重新开发时应满足：

- 通过统一应用框架管理生命周期；
- 通过全局数据机制共享几何和网格；
- 通过组件工厂装配可复用组件；
- 通过操作器承载用户动作和业务执行；
- 通过插件机制接入新的网格生成器；
- 通过抽象接口隔离具体几何内核、网格引擎和文件格式。

具体注册函数、工厂类名和目录组织由技术设计确定，不属于本需求的外部接口约束；但重新开发应保留相同的扩展能力和运行行为。

### 11.5 第五步：验证复用是否合理

每项复用决策至少应回答：

1. 该能力是否属于多个 CAE 应用共有的基础能力？
2. FastCAE 是否已经提供稳定接口或可用组件？
3. 复用后是否能降低开发成本或提高一致性？
4. 复用是否会限制 APPMesh 的业务需求？
5. 如果组件不可用，替代方案能否满足相同验收标准？

## 13. 实现约束与开放问题

### 13.1 实现约束

1. 重新开发应保持统一的全局数据、组件、操作器和插件概念；
2. 内部模块可以采用不同的组织方式，但应保持本规格说明书定义的外部行为；
3. FastCAE 组件可以升级或替换，但替换后必须满足对应功能和验收标准；
4. 后台任务、错误处理和工程数据一致性属于必须满足的质量要求。

### 13.2 开放问题

以下内容不属于当前源码能够确认的首版固定行为，重新开发时应作为实现前置决策：

- 各网格生成器的完整参数集合和默认值；
- 支持的最大几何/网格规模和性能指标；
- 更细的工程文件跨版本兼容策略；当前仅要求校验项目类型和文件版本并尽力恢复；
- 插件签名、权限和安全策略；
- Python/HTTP 的正式版本化 API、参数格式和稳定错误码；
- AI 助手的正式功能边界；
- 物理场和后处理是否纳入后续版本。
